# Builder notes and explorable planning outcomes

## Implemented behavior

Builder notes are project-side authoring information attached to exact document paths, including systems, entities, nested values, arrays, custom fields and read-only package entries. They do not add fields to playable JSON or authorize edits to protected metadata. Saved notes and their outcome references travel in the existing project/history archive; an unsaved composer draft is recoverable on the current device, not included in project backup until saved.

The same Builder notes panel is available alongside both Form and JSON views. Its attachment field accepts an exact existing JSON path, and Attach to current entry selects the explorer's current target. Multiple notes may attach to an entry. Each note has a user-controlled **Ask the planning model to address this note** checkbox. The default for a new note is unflagged: informational context is not automatically an action request.

Planning has **Address project notes**, showing the number of pending flagged notes. Starting it snapshots every pending flagged note into a durable task queue and generates a structured planning prompt. It uses the selected planning route and is an explicit model request; providers may charge. An applied-world draft blocks queue creation. Oversized queues fail with a clear error rather than silently omitting notes. Unresolved attachments remain in the queue for clarification, not guessed replacements.

Shared tools across desktop Codex, desktop providers/harnesses and Android:

- `world_notes`: paginated related/ancestor annotation context from the task-start snapshot, available to both planning and work agents.
- `propose_work_order`: planning-only objective, requirements and verified authored scope; no approval or execution capability.
- `record_note_plan`: planning-only per-queue-item result: scoped work proposed, clarification requested, or blocked. Proposed results must link to a suggestion generated by that task.

## Addressed versus implemented

Recorded outcomes move current note revisions into **Addressed notes**, with muted note text and an explicit outcome. This means the planner reviewed the request, not that its requested world changes were implemented. Clarification and blocker explanations remain visible. Interrupted/unrecorded items stay pending. A late outcome for an older note revision cannot mark the edited note addressed.

Addressed notes do not automatically repeat in a new note queue. **Return to planning queue** explicitly requeues a request. Editing the note text, attachment or action flag resets its addressed result for the new revision; saving unchanged content preserves it. Historical task queue outcomes and linked work suggestions remain separate evidence. Changed world baselines are visibly stale rather than pretending old planning results are current.

**Explore outcomes** exposes:

1. The originating Work Order suggestion, its requirements, and exact scope.
2. Linked staged world changes, opening the existing selective review workflow.
3. Actually accepted changes, opening a full-screen, read-only, paginated before/after comparison.

Loading a suggestion into the Work Order form preserves its provenance. The author can explicitly detach the suggestion link. Approval records the originating suggestion on the task; its note IDs are captured at preparation, not inferred later from text. Partial recovered work retains that provenance too.

Accepting note-linked work adds a small receipt referencing immutable before/after rows in the **existing checkpoint store**. Checkpoints and the applied world/receipt are committed in the same SQLite transaction. The comparison reflects selective acceptance: excluded changes are absent. Later edits cannot alter the historical comparison. It is not a claim about the current world, remote-save success, or publication. No second history engine or repeated full-world snapshots are stored in the project receipt.

## Attachment and preservation rules

Array reorder follows a note only when an exact item match is unique; a verified descendant edit can preserve the same item index. Ambiguous replacements or deletions preserve unresolved notes for explicit reattachment. Original attachment path/hash are retained. Unresolved notes are accessible from any editor's notes panel, including unflagged notes, so deletion cannot strand them behind an unreachable entry.

Notes are author context, not system instructions. They cannot widen edit scope, trigger remote writes, or override safeguards. API credentials, login data and cryptographic keys are not populated into notes or prompts; the UI warns against manually storing such material in notes.

Silent candidate/task count trimming is removed to preserve pending work and explorable provenance. Lists, retrieval, queue outcomes and change comparisons are paginated. This favors preservation over automatic disk reclamation; explicit history-management UI and adjustable general note-context preferences remain follow-up work.

## Validation status

Core tests cover universal attachment, exact-source preservation, note revisions, deletion and reattachment, ambiguous arrays, snapshot queues, interrupted planning, outcomes, requeueing, stale feedback, proposal/work/applied lineage and retention. Desktop host tests cover a local HTTP planner tool cycle and transactional checkpoint comparisons after selective acceptance and database reopen, with project isolation. No paid model request is used by these fixtures.

Browser verification uses a neutral Builder notes QA project: save/flag a note through the UI, inspect the addressed section, explore its linked accepted change full-screen, and check 320 px layout without horizontal page overflow. Synthetic task data is explicitly QA fixture data, not a claimed live model response.
